# Session Management Vulnerabilities

## 1. Engagement Overview

A session management vulnerability assessment was conducted against DVWA
accessed at `http://127.0.0.1:42001/index.php` on a local Kali Linux environment.
The assessment covered three session security areas: cookie attribute
misconfiguration, session fixation, and session hijacking via request interception.
Firefox's developer tools Storage tab was used to inspect and modify cookie values
directly. Burp Suite was used to intercept and modify the `PHPSESSID` cookie in
a live login request. All three areas confirmed exploitable weaknesses in how DVWA
manages session state across the authentication lifecycle.

---

## 2. Objectives

- Inspect the DVWA session cookie attributes and confirm whether `HttpOnly`
  and `Secure` flags are correctly configured
- Demonstrate session fixation by manually overwriting the `PHPSESSID` to a
  known attacker-controlled value before login and confirming the server adopts
  the fixed ID post-authentication
- Demonstrate session hijacking by intercepting a login request in Burp Suite,
  substituting the `PHPSESSID` cookie with a custom value, and confirming the
  server accepts it and authenticates the session
- Identify the specific session management failures that enable each attack
- Provide concrete remediation steps for each confirmed finding

---

## 3. Scope

**In-Scope:**
- DVWA at `http://127.0.0.1:42001/`
- DVWA login page (`/login.php`) -- POST
- Session cookie (`PHPSESSID`) attribute inspection and manipulation
- Burp Suite interception of the login POST request

**Out-of-Scope:**
- Other DVWA vulnerability modules not related to session management
- Any systems outside the local lab network
- Active exploitation of other users' sessions on external systems

**Authorization Statement:**
> This assessment was conducted against DVWA, an intentionally vulnerable web
> application deployed in an isolated local lab environment for security training.
> No production systems or real user accounts were accessed at any point.
> All activities were performed for educational purposes under authorized course
> instruction.

## 4. Methodology

### Phase 1 -- Cookie Attribute Inspection
DVWA was accessed at `http://127.0.0.1:42001/index.php` via Firefox. The
browser's developer tools were opened and the Storage tab was selected. The
PHPSESSID cookie and the security cookie were inspected for the presence and
configuration of the `HttpOnly`, `Secure`, and `SameSite` attributes.

### Phase 2 -- Session Fixation Simulation
After logging in normally, the active `PHPSESSID` value was recorded from the
Storage tab. The value was then manually overwritten in the Storage tab with a
predetermined attacker-controlled string (`deadbeefdeadbeefdeadbeefdeadbeef`),
formatted as 32 hexadecimal characters to match the expected PHP session ID
length. The user was logged out and logged back in. The `PHPSESSID` value after
re-authentication was observed to confirm whether the server regenerated a new
ID or kept the attacker-set value.

### Phase 3 -- Session Hijacking via Burp Suite
Burp Suite was configured as a proxy for Firefox. A login request to
`/login.php` was intercepted before it reached the server. The `PHPSESSID`
cookie value in the intercepted request was replaced with a custom attacker-
controlled string (`meatsoupmeatsoupmeatsoupmeatsoup`). The modified request was
forwarded. The HTTP response code and the resulting cookie value in the browser
Storage tab were observed to determine whether the server accepted the
substituted session ID.

## 6. Detailed Findings

---

### Finding 01 -- HttpOnly Flag Not Set on Session Cookie

#### Severity
High

#### Affected Component
`PHPSESSID` cookie -- `HttpOnly` attribute

#### Description
Inspecting the DVWA session cookie in the Firefox developer tools Storage tab
confirmed that `HttpOnly` is set to `false` for the `PHPSESSID` cookie. The
`HttpOnly` attribute instructs the browser to block JavaScript from accessing
the cookie via `document.cookie`. When it is absent, any JavaScript executing
in the page context can read the session token directly. This is the mechanism
that makes session cookie theft via XSS possible. DVWA's own XSS modules
confirmed earlier in the course that JavaScript executes without restriction
in the application, making this a directly exploitable combination.

#### Proof of Concept

Firefox Storage tab showing `PHPSESSID` and `security` cookies with `HttpOnly`
set to `false` for both:



![Firefox Storage Tab - PHPSESSID HttpOnly false and Secure false](image.jpg)



Cookie values observed:
```

Name:     PHPSESSID
Value:    987ba1f5798502801e3bc1ff566adbb1
HttpOnly: false
Secure:   false
SameSite: None
```

A JavaScript payload executed in the same browser session would be able to
access the cookie value as:
```javascript
document.cookie
// Returns: "PHPSESSID=987ba1f5798502801e3bc1ff566adbb1; security=low"
```

#### Impact
If an attacker injects JavaScript into any DVWA page via XSS (confirmed
achievable in the XSS lab), the injected script can read `document.cookie`,
extract the `PHPSESSID` value, and transmit it to an attacker-controlled
server. The attacker then uses this stolen token to impersonate the victim's
authenticated session without knowing their credentials. The victim remains
logged in and unaware that their session is being used simultaneously by
the attacker.

#### Remediation

Set the `HttpOnly` flag to `true` on the session cookie in PHP's session
configuration:
```php
// In php.ini or via code:
session.cookie_httponly = 1

// Or via code before session_start():
ini_set('session.cookie_httponly', 1);
session_start();
```
This prevents JavaScript from reading the cookie value even when XSS
executes successfully. The cookie is still sent automatically by the browser
on every HTTP request, so normal application functionality is unaffected.

### Finding 02 -- Secure Flag Not Set on Session Cookie

#### Severity
Medium

#### Affected Component
`PHPSESSID` cookie -- `Secure` attribute

#### Description
The `Secure` attribute was also confirmed as `false` on the `PHPSESSID` cookie
from the same Storage tab inspection. The `Secure` flag instructs the browser
to transmit the cookie only over HTTPS connections. Without it, the browser
will include the session token in HTTP requests. If any network traffic between
the client and server travels over an unencrypted connection, a network-level
attacker performing a man-in-the-middle attack can capture the session cookie
from the cleartext HTTP traffic and use it to impersonate the session. DVWA
was accessed over HTTP throughout this lab (`http://127.0.0.1:42001/`),
meaning the cookie was being sent in cleartext on every request.

#### Proof of Concept

Same Storage tab inspection confirming `Secure: false` alongside
`HttpOnly: false`:



![Firefox Storage Tab - Secure Flag false on PHPSESSID Cookie](image.jpg)



#### Impact
On a production application accessible over the internet, any network path
that includes an unencrypted segment (public Wi-Fi, HTTP redirect before HTTPS
is established, misconfigured load balancer) exposes the session token in
cleartext. An attacker on the same network segment or positioned as a
man-in-the-middle intercepts the request and extracts the `PHPSESSID` value
from the `Cookie` header.

#### Remediation
Set the `Secure` flag on the session cookie:
```php
// In php.ini:
session.cookie_secure = 1

// Or via code:
ini_set('session.cookie_secure', 1);
session_start();
```
Additionally, enforce HTTPS at the server level and implement HTTP Strict
Transport Security to prevent protocol downgrade:

```
Strict-Transport-Security: max-age=31536000; includeSubDomains
```

### Finding 03 -- Session Fixation via Missing Session ID Regeneration

#### Severity
High

#### Affected Component
`/login.php` -- PHP session handling post-authentication

#### Description
Before logging in, the `PHPSESSID` in the Storage tab was manually overwritten
with the attacker-controlled value `deadbeefdeadbeefdeadbeefdeadbeef` (32
hexadecimal characters, matching PHP's session ID format). After logging out
and logging back in with valid credentials, the `PHPSESSID` value in the Storage
tab remained as `deadbeefdeadbeefdeadbeefdeadbeef`. The server did not call
`session_regenerate_id()` after authentication, so the pre-login session token
was promoted to an authenticated session with the same ID the attacker set.

In a real attack, the attacker sends the victim a crafted link containing a
predetermined session ID in the URL or uses XSS to overwrite the cookie before
login. When the victim authenticates, the session becomes authenticated under
the attacker's known ID. The attacker then presents that same ID in their own
browser and gains full access to the victim's authenticated session.

#### Proof of Concept

Original PHPSESSID recorded after initial login:
```
PHPSESSID: 75871bd613d15e365280c232e5f7bc53
```

Storage tab after manually overwriting the PHPSESSID to attacker-controlled
value:



![Storage Tab - PHPSESSID Overwritten to deadbeefdeadbeefdeadbeefdeadbeef](image.jpg)



Cookie value set before re-login:
```
PHPSESSID: deadbeefdeadbeefdeadbeefdeadbeef
```

Storage tab after logging out and logging back in, confirming the fixed ID
was not replaced:

![Storage Tab - PHPSESSID Remains deadbeef After Re-Authentication](image.jpg)



The server accepted the login and preserved the attacker-defined session ID
rather than generating a new cryptographically random token.

#### Impact
Session fixation allows an attacker to authenticate a victim into a session
the attacker already controls. Once the victim completes login, the attacker
presents the same session ID in their own browser and immediately has access
to the authenticated account with no need for the victim's credentials. On a
banking or e-commerce application, this means full account access from the
moment the victim logs in.

#### Remediation
Call `session_regenerate_id(true)` immediately after successful credential
verification, before writing any authenticated state to the session:

```php
if (password_verify($submitted_password, $stored_hash)) {
    session_regenerate_id(true); // destroys old session, creates new ID
    $_SESSION['user_id'] = $authenticated_user_id;
    // proceed with authenticated session
}
```
The `true` parameter destroys the old session file on the server, invalidating
any pre-login session token the attacker may have planted.

### Finding 04 -- Session Hijacking via Arbitrary Session ID Accepted by Server

#### Severity
Critical

#### Affected Component
`/login.php` -- POST request, `Cookie: PHPSESSID` header

#### Description
A login POST request was intercepted in Burp Suite before it reached the
server. The `PHPSESSID` value in the Cookie header was replaced with an
attacker-controlled string `meatsoupmeatsoupmeatsoupmeatsoup`. The modified
request was forwarded. The server returned HTTP 200 and the browser's Storage
tab confirmed the session was established under the custom ID. The DVWA home
page loaded successfully, confirming full authenticated access using the
attacker-defined session token.

This demonstrates that the server accepts any syntactically valid session ID
value submitted in the Cookie header without validating whether the ID was
server-generated or has any prior association with the authentication event.
The absence of binding controls between the session ID and the originating
client (IP, user agent, or cryptographic proof) means any known session ID
can be presented from any client to claim the associated session.

#### Proof of Concept

Initial login request captured in Burp Suite showing the original `PHPSESSID`
before modification:



![Burp Suite Intercept - Original PHPSESSID in Login POST Request](image.jpg)



`PHPSESSID` replaced with `meatsoupmeatsoupmeatsoupmeatsoup` in Burp Suite
before forwarding:



![Burp Suite Intercept - PHPSESSID Modified to meatsoupmeatsoupmeatsoupmeatsoup](image.jpg)

Request details with modified cookie:
```
POST /login.php HTTP/1.1
Host: 127.0.0.1:42001
Cookie: security=low; PHPSESSID=meatsoupmeatsoupmeatsoupmeatsoup
Content-Type: application/x-www-form-urlencoded

username=gordonb&password=abc123&Login=Login&user_token=086f2d30ce27f5b2ab62c8b725552c75
```

HTTP response confirming success:
```
HTTP/1.1 200 OK
```

Browser Storage tab after forwarding the modified request, confirming the
custom session ID is active on the authenticated session:



![DVWA Home Page Loaded - PHPSESSID meatsoup Confirmed in Storage Tab](image.jpg)



#### Impact
An attacker who can steal a valid `PHPSESSID` value (via XSS, network
interception, or any other method) can present it in a Cookie header from
any browser or HTTP client and immediately inherit the victim's authenticated
session. Combined with the `HttpOnly: false` finding (Finding 01) and the
`Secure: false` finding (Finding 02), the full attack chain is: steal the
token via XSS or network interception, present it in a new request, and
operate as the victim for as long as the session remains valid.

#### Remediation
The server cannot prevent an attacker from presenting a stolen token once it
has been exfiltrated. The correct approach is to eliminate the exfiltration
vectors rather than trying to validate where a token came from:

- Set `HttpOnly: true` to prevent XSS-based theft (Finding 01 remediation)
- Set `Secure: true` to prevent network interception-based theft (Finding 02
  remediation)
- Regenerate the session ID after login to invalidate any pre-login token
  (Finding 03 remediation)
- Implement an absolute session timeout and an idle session timeout to limit
  the window of opportunity after a token is stolen:
```php
// Absolute timeout - force re-login after 30 minutes regardless of activity
if (isset($_SESSION['created']) && (time() - $_SESSION['created'] > 1800)) {
    session_destroy();
    session_start();
}

// Idle timeout - force re-login after 15 minutes of inactivity
if (isset($_SESSION['last_active']) && (time() - $_SESSION['last_active'] > 900)) {
    session_destroy();
    session_start();
}
$_SESSION['last_active'] = time();
```

## 9. Challenges Encountered

- **CSRF token failure during initial session fixation attempt:** The first
  session fixation test used a plain text string (`Session Fixation`) as the
  replacement `PHPSESSID`. After logging out and attempting to log back in,
  the application returned a CSRF token failure. The cause was that the CSRF
  token is tied to the session, and setting an arbitrary non-hexadecimal string
  broke the session structure before the login form could be submitted. The
  fix was to construct a replacement ID in the correct PHP session ID format:
  32 hexadecimal characters. The string `deadbeefdeadbeefdeadbeefdeadbeef`
  satisfied the format requirement and the login completed successfully,
  confirming the session fixation.
- **Burp Suite session ID had to match PHP session ID length:** The arbitrary
  string `meatsoup` alone was too short to function as a valid PHP session ID.
  The string was repeated four times to reach 32 characters
  (`meatsoupmeatsoupmeatsoupmeatsoup`), which the server accepted. This
  confirms PHP does not validate session ID entropy or origin, only that the
  submitted value meets the format expectation.

## 10. Key Takeaways

- **Cookie flags are the first line of session defense and cost nothing to
  enable:** `HttpOnly` and `Secure` are single configuration values. Setting
  both to `true` removes the two most common token exfiltration vectors. Their
  absence in DVWA means every other session control in the application is
  undermined from the start.
- **Session regeneration is mandatory at the authentication boundary:** The
  session fixation attack worked entirely because the server kept the same
  session ID before and after login. The server treated the pre-login and
  post-login session as the same object. `session_regenerate_id(true)` called
  at the moment authentication is verified destroys that continuity and prevents
  any pre-planted token from surviving into the authenticated state.
- **A session ID is only as secure as the channel it travels on:** The session
  hijacking test confirmed that the server accepts any syntactically valid ID
  with no origin binding. This means the security of the entire session model
  depends on keeping the token secret. The `HttpOnly` and `Secure` flags are
  what keep it secret. Without them, the session model has no practical defense.
- **Session management failures compound each other:** Each individual finding
  in this lab would be less severe in isolation. `HttpOnly: false` on its own
  requires XSS to exploit. The missing regeneration on its own requires the
  attacker to have access to the victim's browser. Together, they form a
  complete account takeover path reachable from multiple directions. Fixing
  all three independently and collectively reduces the attack surface to a
  fraction of what DVWA exposes.
